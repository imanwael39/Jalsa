FE-PERF-001Performance Audit & Baseline P0 High 3h ▾

Task Information

  • Task ID: FE-PERF-001
  • Task Name: Performance Audit & Baseline
  • Owner: M3 (Frontend Lead)
  • Dependencies: All features complete
  • Complexity: High
  • Estimated Effort: 3 hours
  • Priority: Critical

Objective

Run a comprehensive performance audit using Lighthouse, Chrome DevTools, and WebPageTest to establish a baseline for key metrics: First Contentful Paint (FCP), Largest Contentful Paint (LCP), Time to Interactive (TTI), Total Blocking Time (TBT), Cumulative Layout Shift (CLS), and bundle size.

Business Purpose

Measuring performance before optimization allows us to quantify improvements and ensure we meet the target Lighthouse score of ≥ 90.

Technical Purpose

Use Lighthouse CLI and Chrome DevTools to capture performance metrics, identify bottlenecks, and create a report that will be used to track progress.

Prerequisites

  • Application is deployed to a staging environment or running locally with production build.
  • Chrome browser with DevTools.

Dependencies

  • All features: The application must be feature‑complete.

Inputs

  • Production build of the application.

Outputs

  • /docs/performance/baseline-report.md – Baseline metrics report.
  • /docs/performance/optimization-plan.md – Prioritized optimization tasks.

Detailed Workflow

Step 1: Build Production Version

What to do: Run a production build with source maps enabled for debugging.

ng build --configuration=production --source-map

Why it is required: Production builds have optimizations (minification, tree‑shaking) that reflect real performance.

Step 2: Serve the Build Locally or Deploy to Staging

Use a local server (e.g., serve -s dist) or deploy to staging.

npm install -g serve serve -s dist/jalsa-frontend

Step 3: Run Lighthouse Audit

  • Open Chrome DevTools → Lighthouse tab.
  • Select categories: Performance, Accessibility, Best Practices, SEO.
  • Run the audit and capture metrics.

Alternatively, use Lighthouse CLI:

npm install -g lighthouse lighthouse http://localhost:4200 --view --output=html --output-path=./lighthouse-report.html

Step 4: Analyze Web Vitals

Use Chrome DevTools → Performance tab to record a page load and analyze:

  • Main thread activity: Long tasks, JavaScript execution time.
  • Network requests: Waterfall chart, number of requests, total size.
  • Render blocking resources: CSS/JS that delays rendering.

Step 5: Generate Bundle Report

Use ng build --stats-json to generate a stats.json file, then analyze with webpack-bundle-analyzer.

ng build --configuration=production --stats-json npx webpack-bundle-analyzer dist/jalsa-frontend/stats.json

Step 6: Create Baseline Report

Document all metrics with screenshots and notes. Identify the top three performance bottlenecks.

Common Bottlenecks to Look For:
  • Large vendor bundle (node_modules).
  • Unused CSS/JS.
  • Unoptimized images.
  • Render blocking resources.
  • Too many HTTP requests.
  • Inefficient change detection.

Files To Create

  • /docs/performance/baseline-report.md
  • /docs/performance/optimization-plan.md

CLI Commands

ng build --configuration=production --source-map ng build --configuration=production --stats-json npx webpack-bundle-analyzer dist/jalsa-frontend/stats.json lighthouse http://localhost:4200 --view

Concepts Required

  • Core Web Vitals
  • Lighthouse metrics
  • Bundle analysis
  • Performance profiling

Testing Steps

  1. Run the audit three times and average the results.
  2. Document all metrics.

Expected Deliverables

  • Baseline performance report.

Common Mistakes

Mistake 1: Running Lighthouse on a development build (which lacks optimizations).
Fix: Always use production builds.

Definition of Done

  • Baseline report is created and approved.

Team Handoff Notes

  • To: All developers.
  • Key Takeaways: The baseline report guides optimization efforts.
FE-PERF-002Optimize Bundle Size & Lazy Loading P0 High 4h ▾

Task Information

  • Task ID: FE-PERF-002
  • Task Name: Optimize Bundle Size & Lazy Loading
  • Owner: M3 (Frontend Lead)
  • Dependencies: FE-PERF-001
  • Complexity: High
  • Estimated Effort: 4 hours
  • Priority: Critical

Objective

Reduce the bundle size and improve lazy loading by analyzing dependencies, removing unused packages, implementing code splitting, and optimizing Angular build configurations.

Business Purpose

Smaller bundles load faster, reducing Time to Interactive and improving user experience, especially on slower networks.

Technical Purpose

Use webpack-bundle-analyzer to identify large dependencies, enable buildOptimizer, use ngx-quicklink for preloading, and implement route‑level code splitting.

Prerequisites

  • Understanding of Angular build optimization flags.
  • Knowledge of dynamic imports.

Dependencies

  • FE-PERF-001: Baseline report identifying large bundles.

Inputs

  • Bundle analysis report.

Outputs

  • Updated angular.json with optimization settings.
  • Updated routes with lazy loading (already done, but verify).
  • Removed unused dependencies from package.json.
  • Preloading strategy configured.

Detailed Workflow

Step 1: Analyze Bundle Composition

Run webpack-bundle-analyzer and identify large modules:

  • Check if large libraries can be replaced: e.g., moment.js → date-fns, lodash → native or lodash-es.
  • Identify duplicate dependencies: Use npm dedupe or yarn deduplicate.

Step 2: Enable Build Optimizations

Update angular.json production configuration:

// angular.json – production configuration "optimization": { "scripts": true, "styles": true, "fonts": true }, "buildOptimizer": true, "vendorChunk": false, // Disable to avoid large vendor chunk "sourceMap": false // Disable in production

Step 3: Implement Route Preloading

Use PreloadAllModules for critical routes, but consider preloadStrategy with QuicklinkStrategy.

// app.routes.ts import { PreloadAllModules } from '@angular/router'; RouterModule.forRoot(routes, { preloadingStrategy: PreloadAllModules, // Or QuicklinkStrategy });

Install ngx-quicklink for smarter preloading:

npm install ngx-quicklink

Step 4: Remove Unused Dependencies

Use npm ls --depth=0 to list dependencies. Remove any that are not used.

Step 5: Optimize Third‑Party Libraries

  • Use ngx-quill with dynamic import to reduce bundle size.
  • Use chart.js tree‑shakable imports: import { Chart } from 'chart.js/auto'.

Step 6: Verify Improvements

Rebuild and re‑run webpack-bundle-analyzer to confirm bundle size reduction.

Files To Create

  • Updated angular.json
  • Updated app.routes.ts
  • Updated package.json

CLI Commands

npm install ngx-quicklink npm dedupe npm ls --depth=0 ng build --configuration=production --stats-json npx webpack-bundle-analyzer dist/jalsa-frontend/stats.json

Concepts Required

  • Tree shaking
  • Code splitting
  • Lazy loading
  • Preloading strategies

Testing Steps

  1. Rebuild the application.
  2. Verify that the bundle size has decreased.
  3. Test all routes to ensure lazy loading works.

Expected Deliverables

  • Reduced bundle size.

Common Mistakes

Mistake 1: Removing dependencies that are still used indirectly.
Fix: Use npm-check to verify dependency usage.

Definition of Done

  • Bundle size reduced by at least 20% from baseline.

  • To: All developers.
  • Key Takeaways: Lazy loading is critical for performance.
FE-PERF-003Optimize Change Detection & Rendering P0 Medium 4h ▾

Task Information

  • Task ID: FE-PERF-003
  • Task Name: Optimize Change Detection & Rendering
  • Owner: M3 (Frontend Lead)
  • Dependencies: FE-PERF-001
  • Complexity: Medium
  • Estimated Effort: 4 hours
  • Priority: Critical

Objective

Optimize change detection performance by implementing OnPush strategy, using trackBy in loops, optimizing Signals usage, and reducing unnecessary re‑renders.

Business Purpose

Faster rendering improves perceived performance and reduces CPU usage, especially on lower‑end devices.

Technical Purpose

Use ChangeDetectionStrategy.OnPush on all components, implement trackBy for *ngFor, use signal() for fine‑grained reactivity, and avoid heavy computations in templates.

Prerequisites

  • Understanding of Angular change detection.
  • Knowledge of Signals and the OnPush strategy.

Dependencies

  • FE-PERF-001: Baseline report.

Inputs

  • All components.

Outputs

  • Updated components with ChangeDetectionStrategy.OnPush.
  • Updated templates with trackBy.
  • Optimized Signals usage.

Detailed Workflow

Step 1: Apply OnPush Strategy

For all components, add changeDetection: ChangeDetectionStrategy.OnPush.

// In each component import { ChangeDetectionStrategy, Component } from '@angular/core'; @Component({ // ... changeDetection: ChangeDetectionStrategy.OnPush, })

Why it is required: OnPush reduces change detection checks to only when inputs change or events occur.

Step 2: Add trackBy to ngFor

Add trackBy to every *ngFor to avoid re‑rendering entire lists.

<div *ngFor="let item of items; trackBy: trackById">{{ item.name }}</div>

In the component:

trackById(index: number, item: any) { return item.id; }

Step 3: Optimize Signals

  • Use computed() for derived state to avoid unnecessary recalculations.
  • Use effect() sparingly; prefer computed or tap in services.
  • Ensure signals are only updated when values actually change.

Step 4: Avoid Heavy Computations in Templates

Move complex calculations to the component class or use pipes with pure: true.

Step 5: Use Async Pipe for Observables

Always use async pipe for observables to let Angular handle subscription and change detection.

Step 6: Verify Performance

Re‑run Lighthouse and Chrome DevTools to measure rendering improvements.

Files To Create

  • Updated component files.

CLI Commands

No specific CLI commands; manual edits.

Concepts Required

  • ChangeDetectionStrategy.OnPush
  • trackBy
  • Angular Signals optimization
  • Async pipe

Testing Steps

  1. Verify all components use OnPush.
  2. Test that the UI updates correctly.
  3. Re‑run Lighthouse to check for improvements.

Expected Deliverables

  • Optimized change detection across the app.

Common Mistakes

Mistake 1: Using OnPush but mutating objects, preventing change detection.
Fix: Always create new object references (immutable updates).

Definition of Done

  • All components use OnPush, trackBy is used in lists, and Lighthouse rendering metrics improve.

Team Handoff Notes

  • To: All developers.
  • Key Takeaways: Use OnPush and immutable data for performance.

Business Purpose

Technical Purpose

Step 1: Implement Caching in State Services

Use shareReplay(1) for API calls that are reused (e.g., dashboard stats).

// In state service this.http.get(API.dashboard.stats).pipe( shareReplay(1) // Cache the result ).subscribe(...);

Step 2: Debounce Search Inputs

Use debounceTime and distinctUntilChanged for search fields.

this.searchSubject.pipe( debounceTime(300), distinctUntilChanged(), switchMap(term => this.patientService.search(term)) ).subscribe(...);

Step 3: Avoid Duplicate Requests

Use switchMap to cancel pending requests when new input arrives.

Step 4: Use HTTP Interceptors for Caching (Optional)

Implement a caching interceptor for GET requests.

Step 5: Optimize Pagination

Ensure pagination uses server‑side pagination and only fetches the current page.

FE-PERF-005Image & Asset Optimization P1 Medium 3h ▾

Task Information

  • Task ID: FE-PERF-005
  • Task Name: Image & Asset Optimization
  • Owner: M4 (Frontend Developer)
  • Dependencies: FE-PERF-001
  • Complexity: Medium
  • Estimated Effort: 3 hours
  • Priority: High

Objective

Optimize images and assets used in the application: compress images, use modern formats (WebP, AVIF), implement lazy loading, and optimize font loading.

Business Purpose

Images are often the largest resource on a page; optimizing them significantly improves LCP and overall performance.

Technical Purpose

Use ngx-image-cropper or sharp to compress images, convert to WebP/AVIF, implement loading="lazy", and use preconnect for fonts.

Prerequisites

  • Understanding of image formats and optimization tools.

Dependencies

  • FE-PERF-001: Baseline report identifies large images.

Inputs

  • Image assets in src/assets/images/.

Outputs

  • Optimized images (WebP/AVIF).
  • Updated HTML templates with lazy loading.
  • Updated index.html with preconnect/preload hints.

Detailed Workflow

Step 1: Compress Images

Use sharp or imagemin to compress images.

npm install --save-dev sharp

Create a script to convert images:

// scripts/optimize-images.js const sharp = require('sharp'); const fs = require('fs'); const path = require('path'); const inputDir = './src/assets/images'; const outputDir = './src/assets/images/optimized'; if (!fs.existsSync(outputDir)) fs.mkdirSync(outputDir, { recursive: true }); fs.readdirSync(inputDir).forEach(file => { if (file.match(/\.(png|jpg|jpeg)$/i)) { sharp(path.join(inputDir, file)) .resize(1200, 800, { fit: 'inside' }) .webp({ quality: 80 }) .toFile(path.join(outputDir, file.replace(/\.[^.]+$/, '.webp'))); } });

Step 2: Add Lazy Loading to Images

Add loading="lazy" to all images.

<img src="..." loading="lazy" alt="..." />

Step 3: Use Responsive Images

Use srcset and sizes for responsive images.

Step 4: Optimize Font Loading

Use preconnect and preload for fonts.

<link rel="preconnect" href="https://fonts.googleapis.com" /> <link rel="preload" as="font" href="/assets/fonts/cairo.woff2" crossorigin />

Step 5: Verify Improvements

Re‑run Lighthouse and check the LCP and image metrics.

Files To Create

  • scripts/optimize-images.js
  • Optimized images.
  • Updated index.html.

CLI Commands

npm install --save-dev sharp node scripts/optimize-images.js

Concepts Required

  • Image compression
  • WebP/AVIF formats
  • Lazy loading
  • Preconnect/preload

Testing Steps

  1. Verify images load correctly.
  2. Check Lighthouse LCP score improvement.

Expected Deliverables

  • Optimized images and assets.

Common Mistakes

Fix: Balance quality and size; test visually.

FE-RELEASE-001Production Build & Deployment P0 High 3h ▾

Task Information

  • Task ID: FE-RELEASE-001
  • Task Name: Production Build & Deployment
  • Owner: M3 (Frontend Lead)
  • Dependencies: FE-DEPLOY-001, FE-DEPLOY-002
  • Complexity: High
  • Estimated Effort: 3 hours
  • Priority: Critical

Objective

Build the final production version of the application and deploy it to the production environment.

Business Purpose

Deliver the application to end‑users.

Technical Purpose

Execute the production build, verify the artifact, and deploy using the CI/CD pipeline or manual process.

Prerequisites

  • All code is merged to the main branch.
  • All tests pass.
  • Deployment documentation is ready.

Dependencies

  • FE-DEPLOY-001: Build configuration.
  • FE-DEPLOY-002: CI/CD pipeline.

Inputs

  • Main branch source code.

Outputs

  • Deployed application on production.
  • Deployment verification.

Detailed Workflow

Step 1: Create Release Branch/Tag

Tag the main branch with a version number.

git tag -a v1.0.0 -m "Production release v1.0.0" git push origin v1.0.0

Step 2: Trigger Production Deployment

If using CI/CD, the deployment should be triggered automatically on tag push. Otherwise, manually deploy.

npm run build:prod # Deploy the dist/ folder to production server

Step 3: Verify Deployment

Open the production URL and verify the application loads.

Step 4: Monitor Post‑Deployment

Check logs and error monitoring for any issues.

Files To Create

No new files; deployment is executed.

CLI Commands

npm run build:prod git tag -a v1.0.0 -m "Production release" git push origin v1.0.0

Concepts Required

  • Release management
  • Production deployment

Testing Steps

  1. Verify the application loads on production.
  2. Test critical user flows (login, patient CRUD, etc.).

Expected Deliverables

  • Live production application.

Common Mistakes

Mistake 1: Forgetting to update environment variables for production.
Fix: Double‑check environment.prod.ts.

Definition of Done

  • Application is deployed and accessible.

Team Handoff Notes

  • To: Stakeholders, QA, Support.
  • Key Takeaways: Production is live; monitor closely.

FE-MAINT-001Error & Performance Monitoring P0 High 4h ▾

Task Information

  • Task ID: FE-MAINT-001
  • Task Name: Error & Performance Monitoring
  • Owner: M3 (Frontend Lead)
  • Dependencies: FE-RELEASE-001
  • Complexity: High
  • Estimated Effort: 4 hours
  • Priority: Critical

Objective

Set up error monitoring (Sentry, LogRocket) and performance monitoring (Lighthouse CI, Web Vitals) to track the health of the application in production.

Business Purpose

Proactive monitoring allows the team to identify and fix issues before they impact users.

Technical Purpose

Integrate Sentry for error tracking and Google Analytics for performance metrics. Set up alerts for critical errors and performance degradations.

Prerequisites

  • Sentry account with a project set up.
  • Google Analytics or similar tool.

Dependencies

  • FE-RELEASE-001: Production deployment.

Inputs

  • Sentry DSN, GA tracking ID.

Outputs

  • Updated environment.prod.ts with monitoring keys.
  • Sentry integration in main.ts or app.config.ts.
  • Performance monitoring setup.

Detailed Workflow

Step 1: Integrate Sentry

npm install @sentry/angular @sentry/browser
// app.config.ts import { BrowserTracing } from '@sentry/browser'; import * as Sentry from '@sentry/angular'; Sentry.init({ dsn: environment.sentryDsn, environment: environment.production ? 'production' : 'development', integrations: [new BrowserTracing()], tracesSampleRate: 1.0, });

Step 2: Add Sentry Error Handler

Extend the GlobalErrorHandler to send errors to Sentry.

Step 3: Set Up Web Vitals

Use web-vitals to report metrics to Google Analytics or a custom endpoint.

npm install web-vitals
// In main.ts or app.component import { getCLS, getFID, getLCP } from 'web-vitals'; getCLS(console.log); getFID(console.log); getLCP(console.log);

Step 4: Set Up Alerts

Configure Sentry alerts for critical errors and performance issues.

Step 5: Test Monitoring

Trigger a test error and verify it appears in Sentry.

Files To Create

  • Updated environment.prod.ts.
  • Updated app.config.ts.
  • Updated GlobalErrorHandler.

CLI Commands

npm install @sentry/angular @sentry/browser web-vitals

Concepts Required

  • Error monitoring
  • Performance monitoring
  • Sentry integration

Testing Steps

  1. Throw a test error and verify it appears in Sentry.
  2. Check that Web Vitals are being collected.

Expected Deliverables

  • Monitoring system in place.

Common Mistakes

Mistake 1: Not setting the correct environment in Sentry.
Fix: Use environment.production to set the environment.

Definition of Done

  • Error and performance monitoring is active.

Team Handoff Notes

  • To: All developers.
  • Key Takeaways: Monitor Sentry and performance dashboards regularly.
