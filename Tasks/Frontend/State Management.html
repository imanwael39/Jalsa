🧠 Phase 13 – State Management

Purpose: Establish a robust, consistent state management strategy using Angular Signals and RxJS services. This phase consolidates all state‑handling patterns, provides a base framework for feature state services, and ensures that all components access state in a predictable, reactive manner. It covers local component state, shared feature state, application‑wide state, and server (API) state.

📋 Tasks: 6 ⏱️ Total Effort: ~18 hours 👤 Owners: M3 (Frontend Lead), M4 (Frontend Developer) 🔗 Dependencies: All previous feature phases (auth, patients, sessions, exercises, reports, dashboard, chat) 🎯 Deliverable: Complete state management strategy, base utilities, and refactored feature services

Objective

Define a comprehensive state management architecture for the application, outlining how different types of state (local, shared, application, server) are handled, and establishing the patterns and conventions for using Signals and RxJS.

Business Purpose

A clear, documented architecture ensures that all developers follow the same patterns, reducing bugs, improving maintainability, and enabling predictable state updates across the application.

Technical Purpose

Provide a blueprint for state management that leverages Angular Signals for reactive state, RxJS for asynchronous operations, and services for encapsulation. This ensures a consistent approach that is scalable and testable.

Prerequisites

  • Concepts: Understanding of Angular Signals, RxJS, Services, and Dependency Injection.
  • Knowledge: Familiarity with the application's feature modules and data flow.

Dependencies

  • Phase 0: Planning documents provide feature list.
  • Phase 2: Core architecture defines the service layer.

Inputs

  • Existing state services (AppStateService, PatientStateService, etc.) if any.
  • Feature list from planning.

Outputs

  • State management architecture document (/docs/architecture/state-management.md).
  • Decision records for using Signals over NgRx.
  • Guidelines for when to use Signals vs RxJS.

Detailed Workflow

Step 1: Categorize State Types

What to do: Identify all state categories in the application.

Why it is required: Different state types require different management strategies.

State Categories:
  • Local Component State: UI state specific to a component (e.g., form values, dropdown open/closed). Use Angular Signals (signal(), computed()) directly in components.
  • Shared Feature State: Data shared across multiple components within a feature (e.g., patient list, selected patient). Use feature state services with Signals.
  • Application State: Global state used across features (e.g., user authentication, theme, loading indicator, notifications). Use a single AppStateService with Signals.
  • Server/API State: Data fetched from backend APIs. Manage via services that call APIs and update feature state services.
  • URL/Route State: Route parameters, query parameters. Use Angular Router and ActivatedRoute.

Step 2: Select Technologies

What to do: Decide on the technical approach for each state category.

  • Local state: signal(), computed(), effect() (for side effects).
  • Shared/Feature state: Services with signal() and computed(), exposed as readonly signals.
  • Application state: Same as shared state, but global.
  • Server state: Use HttpClient with RxJS, then update Signals in state services. Optionally use switchMap for reactive data fetching.
  • URL state: Use Angular Router.

Why it is required: Clear technology choices prevent confusion and ensure consistency.

Step 3: Define Patterns and Naming Conventions

  • Services: Named XxxStateService for state management (e.g., PatientStateService).
  • Signals: Use private signal and expose as readonly via .asReadonly().
  • Methods: Provide setXxx(), updateXxx(), reset() methods for state modifications.
  • Error Handling: Include error and loading signals in each state service.
  • Side Effects: Use effect() for side effects that don't need to be visible (e.g., logging, saving to localStorage). For async operations, use RxJS with switchMap or tap.

Step 4: Create Architecture Document

Write a comprehensive document covering the above decisions, with examples.

Step 5: Present and Get Approval

Share with the team and principal architect for feedback.

Step 1: Create BaseStateService (Abstract Class)

Define an abstract class with generic type T for the data.

// core/state/base-state.service.ts import { signal, WritableSignal } from '@angular/core'; export abstract class BaseStateService<T> { protected dataSignal: WritableSignal<T | null> = signal(null); protected loadingSignal: WritableSignal<boolean> = signal(false); protected errorSignal: WritableSignal<string | null> = signal(null); readonly data = this.dataSignal.asReadonly(); readonly loading = this.loadingSignal.asReadonly(); readonly error = this.errorSignal.asReadonly(); protected setData(data: T): void { this.dataSignal.set(data); this.errorSignal.set(null); } protected updateData(updater: (current: T | null) => T | null): void { this.dataSignal.update(updater); } protected setError(error: string | null): void { this.errorSignal.set(error); if (error) { this.loadingSignal.set(false); } } protected startLoading(): void { this.loadingSignal.set(true); this.errorSignal.set(null); } protected stopLoading(): void { this.loadingSignal.set(false); } protected reset(): void { this.dataSignal.set(null); this.loadingSignal.set(false); this.errorSignal.set(null); } // Optional: handle async operation protected handleAsync(observable: Observable<R>, onSuccess: (data: R) => void): Observable<R> { this.startLoading(); return observable.pipe( tap({ next: (data) => { onSuccess(data); this.stopLoading(); }, error: (err) => { this.setError(err.message || 'An error occurred'); this.stopLoading(); }, }), catchError((err) => { // Already handled in tap error, but rethrow for component handling return throwError(() => err); }) ); } }

Step 2: Create State Utilities

Provide utility functions for creating state objects quickly.

// core/state/state-utils.ts import { signal, WritableSignal } from '@angular/core'; export function createState<T>(initialValue: T) { const state = signal(initialValue); return { state: state.asReadonly(), set: (value: T) => state.set(value), update: (fn: (current: T) => T) => state.update(fn), reset: () => state.set(initialValue), }; } export function createAsyncState<T>() { const data = signal<T | null>(null); const loading = signal(false); const error = signal<string | null>(null); return { data: data.asReadonly(), loading: loading.asReadonly(), error: error.asReadonly(), setData: (value: T) => { data.set(value); error.set(null); }, setError: (err: string) => { error.set(err); data.set(null); }, startLoading: () => loading.set(true), stopLoading: () => loading.set(false), reset: () => { data.set(null); loading.set(false); error.set(null); }, }; }

Step 3: Create Barrel Export

// core/state/index.ts export * from './base-state.service'; export * from './state-utils';

Step 4: Document Usage

Add examples in the architecture document or inline comments.

// core/state/app-state.service.ts import { Injectable, signal } from '@angular/core'; export interface Notification { id: string; message: string; type: 'success' | 'error' | 'warning' | 'info'; duration?: number; } @Injectable({ providedIn: 'root', }) export class AppStateService { // Theme private themeSignal = signal<'light' | 'dark'>('light'); readonly theme = this.themeSignal.asReadonly(); // Sidebar private sidebarCollapsedSignal = signal(false); readonly sidebarCollapsed = this.sidebarCollapsedSignal.asReadonly(); // Loading (global) private globalLoadingSignal = signal(false); readonly globalLoading = this.globalLoadingSignal.asReadonly(); // Notifications private notificationsSignal = signal<Notification[]>([]); readonly notifications = this.notificationsSignal.asReadonly(); // Methods toggleTheme() { this.themeSignal.update(current => current === 'light' ? 'dark' : 'light'); } setTheme(theme: 'light' | 'dark') { this.themeSignal.set(theme); } toggleSidebar() { this.sidebarCollapsedSignal.update(collapsed => !collapsed); } setSidebarCollapsed(collapsed: boolean) { this.sidebarCollapsedSignal.set(collapsed); } showGlobalLoading() { this.globalLoadingSignal.set(true); } hideGlobalLoading() { this.globalLoadingSignal.set(false); } addNotification(message: string, type: Notification['type'] = 'info', duration: number = 5000) { const id = Date.now().toString(36) + Math.random().toString(36).slice(2); const notification: Notification = { id, message, type, duration }; this.notificationsSignal.update(list => [...list, notification]); if (duration > 0) { setTimeout(() => this.removeNotification(id), duration); } } removeNotification(id: string) { this.notificationsSignal.update(list => list.filter(n => n.id !== id)); } clearNotifications() { this.notificationsSignal.set([]); } }

FE-STATE-005Integrate State Services with Components P0 Medium 3h ▾

Task Information

  • Task ID: FE-STATE-005
  • Task Name: Integrate State Services with Components
  • Owner: M3 (Frontend Lead)
  • Dependencies: FE-STATE-004
  • Complexity: Medium
  • Estimated Effort: 3 hours
  • Priority: Critical

Objective

Update all feature components to use the feature state services instead of directly using services that call APIs. Components should read state from signals and dispatch actions (e.g., load data, update data) through the state services.

Business Purpose

Decouple components from data-fetching logic, making them leaner and easier to test.

Technical Purpose

Components become pure view controllers; they subscribe to state signals and call methods on state services. API calls are triggered by the state services or dedicated service layers, but the state is managed centrally.

Prerequisites

  • Feature state services are available.
  • Components need to be refactored.

Dependencies

  • FE-STATE-004: State services exist.

Inputs

  • Existing components (PatientListComponent, PatientDetailComponent, etc.).

Outputs

  • Refactored components that use state services.

Detailed Workflow

Step 1: Identify Components Using Direct API Calls

List all components that directly inject and use services like PatientService, SessionService, etc.

Step 2: Refactor Each Component

  • Inject the corresponding state service (e.g., PatientStateService).
  • Bind component data to state signals (e.g., patients = this.patientState.data).
  • Replace API calls with state service methods (e.g., this.patientState.loadPatients()). The load method should call the API service and update the state.
  • Ensure loading and error signals are used in the template.

Step 3: Update Templates

Use loading() and error() signals from state service to show spinners and error messages.

Step 4: Test

Verify that components work the same as before, but now use state services.

Step 5: Remove Direct API Calls from Components

Ensure components no longer directly call HttpClient or feature services that contain API calls; those calls should be moved to the state services (or a separate service layer, but state services can delegate to them).

Files To Modify

  • All feature components (list, detail, form, etc.).

CLI Commands

None; manual refactoring.

Concepts Required

  • Angular Signals in templates
  • Component design patterns

Testing Steps

  1. Test each component to ensure data loads correctly.
  2. Test that loading and error states are displayed.

Expected Deliverables

  • All components updated to use state services.

Common Mistakes

Mistake 1: Forgetting to call the load method in ngOnInit.
Mistake 2: Not using the state signals correctly in templates.

Edge Cases

  • If a component can be reused with different data, ensure state is properly isolated.

Definition of Done

  • All components use state services, and all tests pass.

Team Handoff Notes

  • To: All developers.
  • Key Takeaways: Components should not directly fetch data; they should use state services.
